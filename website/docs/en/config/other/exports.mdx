# exports

- **Type:** `boolean | ExportsOptions`
- **Default:** `false`
- **CLI:** `--exports` / `--no-exports`

Whether to generate the `exports` field in `package.json` from the build outputs after a successful build.

- `true`: enable the generation with the default options.
- `false`: disable the generation.
- An object: enable the generation with the [options](#exportsinclude) in it.

```ts title="rslib.config.ts"
export default defineConfig({
  lib: [{ format: 'esm', dts: true }],
  exports: true,
});
```

`exports` is a top-level configuration that applies to the whole package, and cannot be set in a `lib` item. The `--exports` and `--no-exports` CLI options override it with `true` or `false`.

Rslib owns the `exports` field: the generated result replaces the existing value as a whole. Add subpaths and conditions that are not generated with [exports.custom](#exportscustom). The original indentation and line endings are preserved, and the file is not written when nothing changes.

The `exports` field is not generated in watch mode, or when only some libs are built with `--lib`. Run `rslib build` to update it after the entries change.

## Generation rules

- Only outputs in the `esm` and `cjs` formats are exported.
- The `index` entry is exported as `.`, an entry such as `button/index` is exported as `./button`, and other entries are exported by their names, such as `./utils/numbers`.
- When an entry has both `esm` and `cjs` outputs, the value uses the `import` and `require` conditions. When it has only one format, the value is the output path, which applies to every condition, so an ESM-only package can also be loaded by `require(esm)`.
- The `.` subpath comes first, and the other subpaths are sorted.

For example, building `esm` and `cjs` libs with an `index` entry generates:

```json title="package.json"
{
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs"
    }
  }
}
```

### Declaration files

For libs with [dts](/config/lib/dts) enabled, Rslib looks up the declaration file of each output, next to the output, or under [dts.distPath](/config/lib/dts#dtsdistpath) when it is set:

- When the outputs of every format have declaration files with the matching extension next to them (`.d.ts` for `.js`, `.d.mts` for `.mjs`, and `.d.cts` for `.cjs`), no `types` condition is added, as TypeScript finds them on its own.
- Otherwise, a `types` condition shared by all formats is added, preferring the declaration file with the matching extension. Declaration files under a separate `dts.distPath` always need it.
- When no declaration files are found for the outputs of a lib, the build fails.

For example, in a package with `"type": "module"`, when both the `esm` and `cjs` libs enable `dts: true`, the `cjs` output `index.cjs` only has `index.d.ts` next to it instead of the matching `index.d.cts`, so the following is generated:

```json title="package.json"
{
  "exports": {
    ".": {
      "types": "./dist/esm/index.d.ts",
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs"
    }
  }
}
```

To emit declaration files with the matching extension for every format, enable [dts.autoExtension](/config/lib/dts#dtsautoextension) and output each format to a separate directory.

### CSS

In bundle mode, the CSS emitted for an entry is exported, because the JavaScript output does not import it. The subpath is the path of the CSS file relative to the output directory, such as `./index.css` by default. When both the `esm` and `cjs` libs emit it, the `esm` one is used. An entry built only from CSS files only exports its CSS.

```json title="package.json"
{
  "exports": {
    ".": "./dist/index.js",
    "./index.css": "./dist/index.css"
  }
}
```

In bundleless mode, CSS is not exported, as the JavaScript outputs import their own styles.

## exports.include

- **Type:** `string[]`
- **Default:** all entries in bundle mode, and only the `index` entry in the root of [lib.outBase](/config/lib/out-base) in bundleless mode, where every source file is an entry

Glob patterns of the outputs to export. A pattern is matched against the path of each JavaScript or CSS output relative to the output directory of its lib, such as `utils/index.js` or `index.css`, with or without the extension. Writing `index` matches `index.js`, `index.cjs` and `index.css`, while `index.css` matches only the CSS.

For example, to export the main entry and the `index` entry of each component directory in a bundleless component library:

```ts title="rslib.config.ts"
export default defineConfig({
  lib: [{ format: 'esm', bundle: false }],
  exports: {
    include: ['index', '*/index'],
  },
});
```

```json title="package.json"
{
  "exports": {
    ".": "./dist/index.js",
    "./button": "./dist/button/index.js",
    "./input": "./dist/input/index.js"
  }
}
```

## exports.exclude

- **Type:** `string[]`
- **Default:** `[]`

Glob patterns of the outputs to exclude from those selected by [exports.include](#exportsinclude), matched in the same way.

```ts title="rslib.config.ts"
export default defineConfig({
  lib: [{ format: 'esm', bundle: false }],
  exports: {
    include: ['**'],
    exclude: ['internal/**'],
  },
});
```

## exports.source

- **Type:** `boolean | string`
- **Default:** `false`

Whether to export the source files of the entries for development. The source file of an entry must be a single module inside the package root.

- `false`: only export the build outputs.
- `true`: the top-level `exports` points to the source files, and the exports of the build outputs are written to `publishConfig.exports`, which replaces `exports` when packing and publishing with pnpm or Yarn. npm does not support `publishConfig.exports`.
- A string: a condition with this name pointing to the source file is added to each JavaScript subpath, which can be used with the [customConditions](https://www.typescriptlang.org/tsconfig/#customConditions) option of TypeScript, or [@rsbuild/plugin-source-build](https://github.com/rstackjs/rsbuild-plugin-source-build).

For example, `source: '@acme/source'` generates:

```json title="package.json"
{
  "exports": {
    ".": {
      "@acme/source": "./src/index.ts",
      "default": "./dist/index.js"
    }
  }
}
```

## exports.custom

- **Type:**

```ts
type ExportsCustomItem =
  | ExportsField
  | ((
      exports: ExportsField,
      context: { pkg: Record<string, unknown>; isPublish: boolean },
    ) => ExportsField | Promise<ExportsField>);

type ExportsCustom = ExportsCustomItem | ExportsCustomItem[];
```

- **Default:** `undefined`

Customize the generated exports. It can be an object, a function, or an array of them.

- An object adds subpaths to the exports. A subpath with the same key as a generated one replaces it as a whole.
- A function receives the exports and returns the final exports. It can be async. Its second argument provides the content of `package.json` as `pkg`, and `isPublish`, which is `true` when the result is written to `publishConfig.exports`.
- An array applies each item in order, with each item receiving the result of the previous one. When configurations are merged with [mergeRslibConfig](/api/javascript-api/core#mergerslibconfig), the `custom` options that are not both objects are merged into an array.

```ts title="rslib.config.ts"
export default defineConfig({
  exports: {
    custom: (exports) => ({
      ...exports,
      '.': { browser: './dist/browser.js', default: exports['.'] },
      './package.json': './package.json',
    }),
  },
});
```
